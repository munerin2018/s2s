# 構成

## 原則：通信から設計を始めない

先に決めたのは「人・投稿・返信・いいね・フォロー・板・画像・削除をどう表すか」です。
そのあとで「どう見つけ、どう繋ぎ、どう同期し、どう複製するか」を決めました。

順序を逆にすると、トランスポートの都合がデータモデルに染み出します。
実際この方針のおかげで、libp2p のバージョンを v3 から v2 に落としたときも、
`packages/core` は1行も変わりませんでした。

## 層

```
  UI                     packages/ui
    3つの見え方は3つのデータモデルではなく、同じログへの3つのクエリ

  アプリ API             packages/core/src/s2s.js
    post() / reply() / like() … すべて「自分のログに1件追記する」

  ビュー                 packages/core/src/timeline.js
    タイムライン・スレッド・板・通知。すべて派生データで、捨てて作り直せる

  レプリカ               packages/core/src/store.js
    検証・連鎖確認・順序外の保留・索引

  イベント               packages/core/src/event.js
    署名・検証・形の検査

  正準符号化             packages/core/src/codec.js
    署名対象のバイト列を、どの実装でも同一にする

  ─────────────── ここまでがネットワークを知らない ───────────────

  同期                   packages/net/src/sync.js
  メディア               packages/net/src/blobs.js
  ノード                 packages/net/src/network.js
  トランスポート          platform-node.js / platform-browser.js
```

`packages/core` は libp2p を import しません。テストもネットワークなしで走ります。
`packages/net` が core に attach する形で、依存の向きは常に一方向です。

## なぜログが追記専用なのか

`seq` と `prev` の連鎖にしておくと、

- **差分が整数1つで出せます。** 「あなたは 42 まで持っている、私は 47 まである」で終わりです。
  集合照合も Merkle 木も要りません。
- **改竄が検出できます。** 途中を書き換えると以降の `prev` が全部ずれます。
- **完全性が分かります。** 欠番がなければ全部持っていると断言できます。

Secure Scuttlebutt の feed、AT Protocol の repo cursor と同じ考え方です。

## なぜゴシップと同期の両方があるのか

- **ゴシップ**は速いが、聞いていなかった分は届きません
- **同期**は完全だが、能動的に取りに行く必要があります

SNS は「オフラインだった間の投稿」がほとんどなので、同期がないと成立しません。
一方、目の前で起きたことが数十秒遅れるのも使い物になりません。だから両方使います。

さらに `network.js` には **store-and-forward** を入れてあります。
誰かから新しいものを受け取ったら、1.5 秒後に他の接続先にも同期をかけます。
ゴシップのメッシュは接続直後にはまだ張れておらず、
小さい網ではその「接続直後」が一番よく喋る時間帯だからです。

これがないと、A—B—C とつながっていても A と C が互いを知りません。
`packages/net/test/replication.test.js` の3ピアのテストはこれを確かめています。

## なぜ PC 版だけピアが main プロセスにいるのか

ブラウザは TCP ポートを開けず、mDNS も話せません。
Electron の main プロセスは Node なので両方できます。

その結果、PC 版だけが

- 同じ Wi-Fi 内のピアを**設定なしで見つけられる**
- 他のピアから**ダイヤルされる側になれる**
- **サーキットリレー**として、NAT 越しのブラウザ同士を仲介できる

という役回りになります。ウィンドウは IPC 越しの表示係です。

UI のコードを1つに保つため、`packages/ui/src/adapter/` に2つの実装を置き、
同じ API（`snapshot` / `act` / `status` / `mediaUrl`）を見せています。
画面側はどちらで動いているか知りません。

## なぜ Rust 実装があるのか

`rust/s2s-peer` は同じプロトコルを話す独立実装です。存在理由は2つあります。

1. **常時起動用。** Electron 版が数百 MB 使うところを数 MB で済ませます。
2. **仕様の検証。** 2つの独立した実装が通信できるということは、
   プロトコルが片方の実装の都合に寄りかかっていない、ということです。

実際これを書く過程で、正準 JSON の文字列エスケープと varint の符号化が
仕様として曖昧だったことが分かり、`docs/PROTOCOL.md` に明文化しました。

## ライブラリ選定について

js-libp2p は **v2 系**で揃えています。v3 系はストリーム API が刷新されていますが、
2026-09 時点で **gossipsub が v3 に追随していません**（`@chainsafe/libp2p-gossipsub` 14.1.2 は
`@libp2p/interface` v2 系に依存）。混ぜると型は通って実行時に壊れます。

安定を優先して、相互に検証されている v2 系で統一しました。
gossipsub が v3 対応したら移行できます。影響範囲は `packages/net/src/protocol.js` の
フレーミング（`lpStream` の import 元）だけです。
