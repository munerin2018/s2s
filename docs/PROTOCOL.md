# S2S プロトコル仕様 v1.0.0

この文書は、別実装を書くのに足りるだけのことを書いています。
実際 `packages/` の JavaScript と `rust/s2s-peer/` の Rust は、この文書だけを共通の根拠として
互いに通信しています。

---

## 1. 識別子

すべての識別子は「1文字の接頭辞 + base58btc」です。接頭辞を見れば何を指しているか分かります。

| 接頭辞 | 意味 | 中身 |
|---|---|---|
| `@` | 人 | ed25519 公開鍵 32 バイト |
| `%` | イベント | 署名済みイベントの sha256 |
| `&` | メディア | バイト列そのものの sha256 |

例: `@3v4hFazSseKTjqaYKPNxnhv1w1iMQyCZmeUzvgGwDLom`

**アカウント登録は存在しません。鍵を作った時点で人が存在します。**

## 2. 正準 JSON

署名とハッシュの対象になるバイト列は、必ずこの規則で作ります。
**ここが 1 バイトでもずれると、その著者のログはそこから先、実装をまたいで複製されなくなります。**
再接続しても直りません。だから規則は厳密で、曖昧なものは受理せず拒否します。

1. オブジェクトのキーは**コードポイント順**にソートする
2. 余分な空白を入れない
3. 値が `undefined`（Rust では欠損）のメンバーは出力しない
4. 配列の順序は意味を持つので保持する
5. 文字列のエスケープは `JSON.stringify` と同じ
   （`"` `\` と制御文字のみ。非 ASCII はそのまま UTF-8 で出す）
6. 数値は **`Number.MAX_SAFE_INTEGER` 以内の整数だけ**

```
canonical({b:1, a:2})      →  {"a":2,"b":1}
canonical({a:[3,1]})       →  {"a":[3,1]}
canonical("日本語 🚀")      →  "日本語 🚀"
```

### キー順が「コードポイント順」である理由

JavaScript の `Array#sort` は UTF-16 コード単位で比較します。
サロゲートペアは U+E000 より小さい値なので、`🚀`(U+1F680) が `\uFFFD` より**前**に来ます。
一方、UTF-8 のバイト列で比較する実装（Rust の `str` など）では**後**になります。

絵文字をキーに含むオブジェクトで、この 2 つは逆の結果を出します。
そこで JS 側が明示的にコードポイント順で並べ替え、両者を一致させています。

### 数値が「整数だけ」である理由

`JSON.stringify(1.0)` は `1`、Rust の `serde_json` は `1.0` を出します。
同じ値なのにバイト列が違うので、署名が一致しません。

したがって小数は**両実装とも拒否**します。
ただし `1.0` のように**整数値の小数は、整数に正規化**します。
`JSON.parse("1.0")` は JavaScript 側で整数 `1` になり、元のテキストが `1.0` だったことを知る方法がないためです。
ここで Rust だけが拒否すると、細工したイベントを「JS は受理し Rust は拒否する」状態にでき、
ネットワークを意図的に分断できてしまいます。

`Number.MAX_SAFE_INTEGER`（2^53-1）を超える整数も、丸め方が違うので拒否します。

### 適合性ベクタ

[canonical-vectors.json](canonical-vectors.json) に、入力と期待される出力の組が入っています。
**JavaScript と Rust の両方が、このファイルを読んでテストします。**
新しい実装を書くときも、まずこれを通してください。

## 3. イベント

ユーザーの行為はすべて1つのイベントであり、その人自身のログに追記されます。

```json
{
  "author":  "@...",
  "seq":     1,
  "prev":    null,
  "ts":      1758000000000,
  "kind":    "post",
  "content": { "text": "こんにちは" },
  "sig":     "base58 の ed25519 署名",
  "id":      "%..."
}
```

| 欄 | 説明 |
|---|---|
| `author` | 著者の識別子 |
| `seq` | そのログの中での位置。1 始まり、欠番なし |
| `prev` | `seq-1` のイベントの `id`。`seq === 1` のときのみ `null` |
| `ts` | 著者が主張する時刻（unix ミリ秒）。**参考値であって信頼できません** |
| `kind` | 下表のいずれか |
| `content` | `kind` ごとの構造 |
| `sig` | 署名（下記） |
| `id` | イベント識別子（下記） |

### 署名と id

```
body      = { author, seq, prev, ts, kind, content }
sig       = base58( ed25519_sign( secretKey, utf8(canonical(body)) ) )
id        = "%" + base58( sha256( utf8(canonical({ ...body, sig })) ) )
```

**`id` が署名まで含めてハッシュしている**のが要点です。
これにより、本文だけ同じで署名を差し替えた別イベントを作ることができません。

### kind 一覧

| kind | content |
|---|---|
| `profile` | `{ name, bio?, avatar? }` |
| `post` | `{ text, media?, tags?, board? }` |
| `reply` | `{ root, parent, text, media? }` |
| `like` | `{ target, value: 1 \| -1 }` |
| `repost` | `{ target }` |
| `follow` / `unfollow` | `{ target: "@..." }` |
| `block` / `unblock` | `{ target: "@..." }` |
| `thread` | `{ board, title, text, media? }` |
| `delete` | `{ target: "%..." }` |

`media` の各要素は `{ blob: "&...", mime, w?, h?, alt? }` です。

制限値（`packages/core/src/event.js` の `LIMITS`）:
`text` 2000 / `name` 64 / `bio` 400 / `title` 120 / `board` 48 / `media` 8 件 / `tags` 12 件。
`ts` は現在時刻 + 5 分より未来なら拒否します。

## 4. 受信時の検証

ピアから受け取ったイベントは、次をすべて満たしたときだけ保存します。

1. 形が正しい（`kind` が既知、`content` が `kind` に合っている、制限値内）
2. **`content` に、その `kind` で定義されていないメンバーがない**
3. `seq === 1` なら `prev === null`、そうでなければ `prev` がイベント id である
4. `ts` が 0 以上で、未来すぎない
5. **`sig` が `author` の公開鍵で検証できる**
6. **`id` が `canonical({...body, sig})` の sha256 と一致する**
7. `seq` が手元の head + 1 である
8. `prev` が手元の head の `id` と一致する

7 を満たさず `seq` が先に進みすぎている場合は**保留**し、間が埋まったら適用します
（ゴシップは順序を保証しないため、これは日常的に起こります）。
保留バッファには**著者ごとと全体の両方に上限**があります。
鍵はいくらでも作れるので、著者ごとの上限だけでは意味がありません。

同じ `seq` に別の `id` のイベントが来たら**フォーク**として拒否します。
これは著者が2つの履歴に署名したことを意味し、検出はできますが自動修復はしません。

### 2 が必要な理由

`content` の未知メンバーを黙って許すと、「片方の実装だけが受理するイベント」を作れてしまいます。
そのイベントが入ったログは、そこから先そちら側にしか伝播しません。

### トップレベルの余分なフィールドは剥がす

署名と `id` は `author / seq / prev / ts / kind / content / sig` しか覆っていません。
つまり、正当なイベントに任意のフィールドを貼り付けても検証は通ります。
そのまま保存・転送すると、ネットワーク全体を使った増幅になります。

そこで**検証を通ったあと、定義された 8 つのメンバーだけで作り直してから**保存・転送します。
`content` は署名対象の内側なので触りません（触ると署名が壊れます）。だから上の 2 で拒否します。

### delete の順序

`delete` は、対象イベントの著者と `delete` の著者が一致するときだけ効きます。

**対象をまだ受け取っていない場合は、保留します。**
著者を確認できないまま適用すると、「まだ届いていないイベントの id を先に指定する」だけで
誰でも任意の投稿を隠せてしまうからです。ゴシップは順不同なので、これは日常的に起こります。

これは**墓標**であって消去ではありません。受け取っていない相手には効きません。

## 5. ネットワーク

libp2p 上の3つの仕組みで動きます。

| | |
|---|---|
| gossip `s2s/v1/events` | 新しいイベントを即座にばらまく |
| `/s2s/1.0.0/sync` | 互いに足りないものを埋める |
| `/s2s/1.0.0/blob` | メディアをハッシュ指定で取りに行く |

**ゴシップだけでは足りません。** オフラインの間に流れたものは受け取れないからです。
接続時と 30 秒ごとに sync を回すことで、完全性を担保します。

### 5.1 have ベクタ

```json
{ "@alice": 42, "@bob": 7 }
```

「そのログをどこまで持っているか」を著者ごとに1つの整数で表します。
ログが厳密な連鎖であるため、差分はこの1つの数だけで正確に出せます。
集合照合も Merkle 木も bloom filter も要りません。

### 5.2 sync の手順

フレーミングは **varint 長さ前置 + JSON**（`it-length-prefixed` 互換の符号なし LEB128）です。

厳密に交互なので、どちらの側も相手待ちで詰まりません。

```
発信側 → { "type":"have", "vector": {...} }
発信側 ← { "type":"have", "vector": {...} }
発信側 → { "type":"events", "events":[...] } ×N , { "type":"end" }
発信側 ← { "type":"events", "events":[...] } ×N , { "type":"end" }
```

応答側は読み書きの順序が逆になります（have を読む → have を書く → events を読む → events を書く）。

1メッセージあたり最大 200 イベント、1フレーム最大 4 MiB、1回の同期で最大 10,000 メッセージ。

### have ベクタの検証

**ベクタの中身は相手が自由に決められます。** 受け取った側は次を捨ててから使います。

- 著者 id の形をしていないキー
- 非負整数でない値（負数・小数・文字列・`null` など）
- 50,000 件を超えた分

特に負の値は危険です。`-1e12` のような値を1つ送るだけで、
送信ループが `await` を挟まないまま数十億回まわり、イベントループ全体が停止します。
検証がないと、数バイトのメッセージ1通でピアを丸ごと止められます。

### 5.3 blob

```
要求側 → { "blob": "&..." }
要求側 ← { "ok": true, "size": 12345 }   （持っていなければ { "ok": false }）
要求側 ← <バイト列>
```

受け取ったバイト列は必ず sha256 を取り直して、要求した `&...` と一致するか確認します。
**名前がハッシュそのものなので、嘘をつくピアはこれだけで検出できます。**

最大 16 MiB。

### blob id は必ずデコードしてから使う

要求された文字列は**名前ではなく主張**です。そのままファイルパスに連結してはいけません。

```
{"blob":"&../identity.json"}   →  <dir>/blobs/../identity.json  =  <dir>/identity.json
{"blob":"&/etc/passwd"}        →  絶対パスは join で置換される
{"blob":"&日本"}                →  バイト境界でないスライスは Rust でパニック
```

1つ目は**アカウントの秘密鍵をそのまま送信してしまいます**。

正しくは、32 バイトにデコードしてから**再エンコードした名前だけ**を使います。
こうするとファイル名は有効なハッシュのいずれかにしかなりません。

## 6. トランスポート

| 実行環境 | 使うもの |
|---|---|
| PC・ネイティブ | TCP、WebSocket、mDNS、サーキットリレー（提供側） |
| ブラウザ・スマホ | WebSocket、WebRTC、サーキットリレー（利用側） |

暗号は noise、多重化は yamux。いずれも libp2p の標準です。

**libp2p のピア ID と S2S のアカウントは別の鍵です。**
前者はネットワーク上の端点、後者は人を指します。
同じ鍵にすると、接続しただけで相手に自分の人格が知られてしまいます。

## 7. データディレクトリ

JS 実装と Rust 実装で共通です。

```
<dir>/
  identity.json     { "id": "@...", "secretKey": "base58" }   ← これがアカウント本体
  events.jsonl      1行1イベントの追記専用ログ
  blobs/<base58>    メディアの実体（ファイル名 = ハッシュ）
```

Web 版では同じものが IndexedDB の `events` / `blobs` / `meta` ストアに入ります。
